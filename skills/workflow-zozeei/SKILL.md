# Workflow Zozeei

นำทางจากความต้องการไปสู่แผนและการลงมือที่ตรวจผลได้
เลือกเฉพาะขั้นตอนที่จำเป็นตามความชัดเจน ขนาด และความเสี่ยงของงาน

## ขอบเขตและกฎการทำงาน

- ทำตามคำสั่งผู้ใช้และกฎโปรเจกต์ ภายใต้ข้อกำหนดของระบบและเครื่องมือ
- หากผู้ใช้ขอแผน ให้ส่งแผน หากขอให้ลงมือด้วย
  ให้ดำเนินการภายในขอบเขตและสิทธิ์ที่ได้รับ
- รักษาการอนุมัติที่ได้รับแล้ว ไม่ถามซ้ำสำหรับการกระทำเดิม
- การขอแผนไม่ใช่การอนุญาตให้สร้าง issue ติดตั้ง dependency
  เปลี่ยนข้อมูล หรือ deploy
- ตรวจสกิลที่พร้อมใช้และอ่านคำแนะนำก่อนเรียก
  ตรวจว่าหน้าที่ตรงกับงาน ไม่ตัดสินจากชื่อเพียงอย่างเดียว
  และใช้เฉพาะส่วนที่เกี่ยวข้อง
- หากไม่มีสกิลที่ต้องการ ให้แจ้งสั้น ๆ และใช้ขั้นตอนในเฟสนั้นแทน
  โดยไม่อ้างว่าได้เรียกสกิลนั้นหรือพยายามติดตั้งเอง
- สกิลนี้ไม่รวมสกิลที่อ้างถึงไว้ภายใน และไม่ต้องมีสกิลเหล่านั้น
  เพื่อใช้ขั้นตอนพื้นฐาน ใช้กลไกเรียกสกิลของเครื่องมือที่กำลังทำงานอยู่
- เริ่มจากข้อมูลหรือแผนที่มีอยู่แล้ว
  ไม่ย้อนทำเฟสที่เสร็จแล้วโดยไม่มีเหตุผล

## หลักที่ต้องรักษา

- Security & Auth: รักษา authentication และ authorization
  ตามข้อกำหนด รวมถึงสิทธิ์ต่อข้อมูลหรือทรัพยากรที่เข้าถึง
- Trust Boundaries: ตรวจข้อมูลภายนอกที่ขอบเขตความเชื่อถือ
  ใช้กลไกเดิมของระบบและหลีกเลี่ยงการตรวจซ้ำที่ไม่มีเหตุผล
- Data Integrity: จัดการความล้มเหลวที่กระทบข้อมูล
  ใช้ transaction เมื่อหลายการเขียนต้องสำเร็จหรือล้มเหลวร่วมกัน
- External Effects: เมื่อมีผลข้างเคียงข้ามระบบ
  พิจารณากรณีสำเร็จเพียงบางส่วนและการเรียกซ้ำตามความเสี่ยงจริง
  transaction ฐานข้อมูลไม่สามารถย้อนผลของ API ภายนอกได้
- Correctness: ตอบ requirement ให้ครบและรักษาพฤติกรรมเดิม
  ที่อยู่นอกขอบเขตการเปลี่ยนแปลง

## เลือกจุดเริ่มต้น

- ความต้องการยังคลุมเครือ: Phase 1
- ความต้องการชัด แต่ยังต้องเลือกวิธี: Phase 2
- เลือกวิธีแล้วและมีหลายขั้นตอน: Phase 3
- มีแผนพร้อมและได้รับอนุญาตให้ลงมือ: Phase 4
- งานเล็กและชัดเจน: ใช้แนวทางสั้นและการตรวจผลที่เกี่ยวข้อง

ประเมินความเสี่ยงจากพฤติกรรมและข้อมูลที่ได้รับผลกระทบ
ไม่ใช้จำนวนบรรทัดที่แก้เป็นเกณฑ์เพียงอย่างเดียว

### กรณีแก้บั๊กหรือ regression — diagnosing-bugs

เมื่อรายงานพฤติกรรมผิดพลาด ให้ใช้ `diagnosing-bugs` หากพร้อมใช้
เพื่อหาสาเหตุจากหลักฐานก่อนเลือกวิธีแก้

หากไม่มีสกิล ให้ตรวจอาการและเส้นทางที่ผิดพลาดโดยตรง
แยกข้อเท็จจริง สมมติฐาน และสิ่งที่ยังต้องตรวจสอบ
อาการที่ชัดเจนไม่ได้แปลว่าสาเหตุชัดเจน

เมื่อมีหลักฐานเพียงพอสำหรับเลือกวิธีแก้ ให้เข้าสู่เฟสที่เกี่ยวข้อง

## Phase 1: ทำความต้องการให้ชัด — grilling / grill-me

ใช้สกิลสำหรับซักถามและทดสอบแนวคิดตามชื่อที่มีอยู่จริง
ในสภาพแวดล้อม เช่น `grilling` หรือ `grill-me`

1. สรุปเป้าหมายและข้อมูลที่ทราบแล้ว
2. ตรวจข้อมูลและโค้ดที่เกี่ยวข้องตามวิธีของโปรเจกต์
   ก่อนถามสิ่งที่ค้นหาได้เอง
3. ถามทีละข้อเฉพาะประเด็นที่กระทบการตัดสินใจ:
   พฤติกรรม ขอบเขต สิทธิ์ ข้อมูล และกรณีผิดพลาดที่สำคัญ
4. ระบุสมมติฐานที่สำคัญให้ผู้ใช้เห็น

หากข้อมูลเพียงพอแล้ว ให้ข้ามการสัมภาษณ์

จบเฟสเมื่อทราบเป้าหมาย ขอบเขต และเงื่อนไขสำเร็จ
เพียงพอสำหรับเลือกแนวทาง

## Phase 2: เลือกวิธีที่เรียบง่าย — ponytail

ใช้ `ponytail` เพื่อเลือกวิธีที่ซับซ้อนน้อยที่สุด
และยังตอบข้อกำหนดครบ

พิจารณาตามลำดับ:

1. YAGNI: จำเป็นต้องเพิ่มหรือเปลี่ยนโค้ดจริงหรือไม่?
2. Reuse: โค้ดหรือ pattern เดิมนำมาใช้ได้หรือไม่?
3. Stdlib: Standard library รองรับหรือไม่?
4. Platform Native: ภาษา platform หรือ framework รองรับหรือไม่?
5. Existing Dependencies: แพ็กเกจที่ติดตั้งแล้วเหมาะกับงานหรือไม่?
6. Clarity: เขียนให้ตรงไปตรงมาและอ่านง่ายขึ้นได้หรือไม่?
7. Minimum Code: หากต้องเขียนใหม่ ใช้โค้ดน้อยที่สุด
   ที่ยังถูกต้อง ชัดเจน และตรวจสอบได้

หยุดเมื่อพบวิธีที่ตอบโจทย์ครบ ไม่จำเป็นต้องรายงานครบทุกข้อ
เสนอทางเลือกเพิ่มเมื่อมีข้อแลกเปลี่ยนที่ผู้ใช้ต้องตัดสินใจ

จบเฟสเมื่อเลือกแนวทางได้ พร้อมเหตุผลและผลกระทบที่สำคัญ

## Phase 3: แตกงานที่ตรวจผลได้ — to-tickets

ใช้ `to-tickets` เมื่อสกิลพร้อมใช้และขอบเขตตรงกับงาน
หากไม่มี ให้แตกงานเป็นรายการในคำตอบโดยตรง

แต่ละงานระบุ:

- ผลลัพธ์ที่ต้องได้
- ขอบเขตหรือไฟล์ที่เกี่ยวข้องเท่าที่ตรวจสอบแล้ว
- Dependency ระหว่างงาน หากมี
- Acceptance criteria
- วิธีตรวจผล

เรียงงานตาม dependency และให้แต่ละงานตรวจผลได้
งานเล็กใช้ checklist สั้นได้

สร้าง issue ภายนอกเฉพาะเมื่ออยู่ในคำขอและสิทธิ์ที่ได้รับ

จบเฟสเมื่อทราบลำดับลงมือและวิธีพิสูจน์ว่างานแต่ละข้อสำเร็จ

## Phase 4: ลงมือและตรวจผล — tdd / ponytail-review / code-review

เริ่มเมื่ออยู่ในขอบเขตคำขอและผ่านเงื่อนไขของโปรเจกต์แล้ว

### พัฒนา — tdd และ ponytail

- ใช้ `tdd` สำหรับงานที่เหมาะกับการทดสอบพฤติกรรม
  ผ่านจุดเรียกใช้งานจริง เช่น endpoint หรือ public API
- ยืนยันว่า test ล้มเหลวด้วยเหตุผลที่คาดไว้ก่อนเพิ่ม implementation
- ใช้หลัก `ponytail` เพื่อเขียนโค้ดเท่าที่จำเป็นให้พฤติกรรมถูกต้อง
- งานที่ไม่เหมาะกับ TDD ใช้วิธีตรวจผลตามลักษณะงาน
- รันการตรวจในสภาพแวดล้อมที่ปลอดภัยตามกฎโปรเจกต์

### เมื่อผลตรวจล้มเหลวผิดคาด

- แยก test ที่ตั้งใจให้ล้มเหลวในขั้น Red ของ TDD
  ออกจากความล้มเหลวที่ไม่คาดหมาย
- ตรวจสาเหตุและดำเนินการตามกฎโปรเจกต์
  โดยแยกปัญหาจาก implementation, test และ environment
- รักษา assertion ที่พิสูจน์ requirement
  ไม่ลดความเข้มหรือข้ามการตรวจเพียงเพื่อให้ผ่าน
- หากตรวจต่อไม่ได้ ให้รายงานข้อจำกัด
  และระบุผลลัพธ์ที่ยังยืนยันไม่ได้

### ตรวจความเรียบง่าย — ponytail-review

ใช้ `ponytail-review` เมื่อต้องตรวจความซับซ้อนหรือโค้ดส่วนเกิน
เน้น abstraction, dependency และความยืดหยุ่นที่ยังไม่จำเป็น
รักษาการตรวจสิทธิ์ validation และความถูกต้องของข้อมูลไว้

### ตรวจ requirement และมาตรฐาน — code-review

ใช้ `code-review` เมื่อต้องตรวจการเปลี่ยนแปลงเทียบกับ
requirement และมาตรฐานของโปรเจกต์

หากกระทบสิทธิ์หรือ trust boundary
ให้ระบุประเด็น security ที่ต้องตรวจเพิ่มเติมอย่างชัดเจน

เลือกความเข้มของการรีวิวตามขอบเขตและความเสี่ยง

### ตรวจสอบ findings ก่อนแก้ตามรีวิว

- ตรวจสอบข้อเสนอจากรีวิวกับโค้ด requirement และหลักฐาน
  ก่อนลงมือแก้
- แก้เฉพาะข้อที่ยืนยันได้และอยู่ในขอบเขตงาน
- หากข้อเสนอไม่ถูกต้องหรือขัด requirement
  ให้อธิบายเหตุผลพร้อมหลักฐานที่เกี่ยวข้อง
- หากข้อเสนอทำให้ขอบเขตเปลี่ยน
  ให้สรุปผลกระทบและดำเนินการตามสิทธิ์ที่ได้รับ
- หลังแก้ตามรีวิว ให้รันการตรวจที่ได้รับผลกระทบอีกครั้ง

จบเฟสเมื่อ acceptance criteria มีหลักฐานรองรับ
รายงานสิ่งที่ยังตรวจไม่ได้และเหตุผล
ผลรีวิวเพียงอย่างเดียวไม่ยืนยันว่าทดสอบผ่านหรือพร้อม deploy

## รูปแบบคำตอบ

ปรับความยาวตามขนาดงาน โดยให้ผู้ใช้เห็น:

1. ความเข้าใจงานและสมมติฐานสำคัญ
2. เฟสหรือสกิลที่เลือก พร้อมเหตุผลสั้น ๆ
3. ขั้นตอนถัดไปและวิธีตรวจความสำเร็จ

หลังลงมือ รายงานสิ่งที่เปลี่ยน ผลตรวจที่รันจริง
และข้อจำกัดที่ยังเหลือ
