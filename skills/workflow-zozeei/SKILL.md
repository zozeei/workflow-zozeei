# Workflow Zozeei

นำทางจากความต้องการไปสู่แผนและการลงมือที่ตรวจผลได้
เลือกเฉพาะขั้นตอนที่จำเป็นตามความชัดเจน ขนาด และความเสี่ยงของงาน

## ขอบเขตและกฎการทำงาน

- ทำตามคำสั่งผู้ใช้และกฎโปรเจกต์ ภายใต้ข้อกำหนดของระบบและเครื่องมือ
- หากผู้ใช้ขอแผน ให้ส่งแผน หากขอให้ลงมือด้วย
  ให้ดำเนินการภายในขอบเขตและสิทธิ์ที่ได้รับ
- ลำดับขั้นตอนมาก่อนการทำแผน: แม้กฎโปรเจกต์หรือระบบ (เช่น `CLAUDE.md`, Planning Mode) จะกำหนดให้วางแผนก่อนเริ่มทำ แต่หากความต้องการยังคลุมเครือ ต้องซักถาม (Grilling) ให้ได้ข้อสรุปก่อนเสมอ ห้ามชิงสร้าง implementation plan เพื่อสนองกฎจนข้ามการถาม
- สิทธิ์การใช้เครื่องมือใน Phase 1–3 เป็นแบบอ่านอย่างเดียว (Read-only): ใช้เฉพาะเครื่องมือสำรวจและอ่านข้อมูล (ค้นหาไฟล์, อ่านโค้ด, ตรวจ schema) ห้ามแก้ไขซอร์สโค้ด สร้างไฟล์ใหม่ หรือรันคำสั่งที่เปลี่ยนแปลงสถานะโปรเจกต์จนกว่าจะผ่านการอนุมัติเข้า Phase 4
- หยุดรอคำตอบเมื่อความต้องการยังไม่ชัด: หากอยู่ใน Phase 1 ที่ยังมีข้อสงสัยหรือทางเลือกสำคัญที่กระทบต่อสถาปัตยกรรม/ขอบเขต ให้ถามและหยุดรอคำตอบ ห้ามสร้างแผนงาน (implementation plan) หรือแตกตั๋วงานล่วงหน้าเด็ดขาด
- หยุดรออนุมัติก่อนลงมือจริง: นำเสนอแผนงานและรอการยืนยันหรืออนุมัติจากผู้ใช้ก่อนเข้า Phase 4
  เว้นแต่ผู้ใช้จะระบุให้ลงมือทำทันทีตั้งแต่ต้น หรืองานเป็นงานแก้ไขเล็กน้อยที่ชัดเจน
- ขออนุมัติใหม่เมื่อขอบเขตเปลี่ยน มี breaking changes ลบโค้ดหรือไฟล์สำคัญ หรือต้องติดตั้ง dependency เพิ่ม
- รักษาการอนุมัติที่ได้รับแล้ว ไม่ถามซ้ำสำหรับการกระทำเดิมในขอบเขตที่ตกลงไว้
- ป้องกันความเสียหาย Git และฐานข้อมูล:
  - ห้ามใช้คำสั่งทำลายข้อมูลหรือย้อนสถานะแบบกู้คืนไม่ได้ (เช่น `git reset --hard`, ลบ branch/ไฟล์สำคัญนอกขอบเขต)
  - ห้ามรันคำสั่ง `git add`, `git commit` หรือ `git push` โดยพลการ เว้นแต่ผู้ใช้จะสั่งเจาะจง ให้สิทธิ์การตรวจ diff และ commit เป็นของผู้ใช้เสมอ
  - ห้ามแก้ไข schema หรือข้อมูลในฐานข้อมูล (เช่น รัน migration, รัน query แก้ไข/ลบข้อมูล, reset หรือ seed ฐานข้อมูล) โดยพลการ หากจำเป็นต้องยุ่งกับฐานข้อมูล ต้องระบุในแผนและขออนุมัติเจาะจงจากผู้ใช้ก่อนเสมอ
- การขอแผนไม่ใช่การอนุญาตให้สร้าง issue ติดตั้ง dependency
  เปลี่ยนข้อมูล หรือ deploy
- ตรวจสกิลที่พร้อมใช้และอ่านคำแนะนำก่อนเรียก
  ตรวจว่าหน้าที่ตรงกับงาน ไม่ตัดสินจากชื่อเพียงอย่างเดียว
  และใช้เฉพาะส่วนที่เกี่ยวข้อง
- หากไม่มีสกิลที่ต้องการ ให้แจ้งสั้น ๆ และใช้ขั้นตอนในเฟสนั้นแทน
  โดยไม่อ้างว่าได้เรียกสกิลนั้นหรือพยายามติดตั้งเอง
- สกิลนี้ไม่รวมสกิลที่อ้างถึงไว้ภายใน และไม่ต้องมีสกิลเหล่านั้น
  เพื่อใช้ขั้นตอนพื้นฐาน ใช้กลไกเรียกสกิลของเครื่องมือที่กำลังทำงานอยู่
- เริ่มจากข้อมูลหรือแผนที่มีอยู่แล้ว
  ไม่ย้อนทำเฟสที่เสร็จแล้วโดยไม่มีเหตุผล

## หลักที่ต้องรักษา

- Security & Auth: รักษา authentication และ authorization
  ตามข้อกำหนด รวมถึงสิทธิ์ต่อข้อมูลหรือทรัพยากรที่เข้าถึง
  ไม่เปิดเผย บันทึก หรือ commit ข้อมูลลับ (เช่น API keys, credentials, tokens, .env)
- Trust Boundaries: ตรวจข้อมูลภายนอกที่ขอบเขตความเชื่อถือ
  ใช้กลไกเดิมของระบบและหลีกเลี่ยงการตรวจซ้ำที่ไม่มีเหตุผล
- Data Integrity: จัดการความล้มเหลวที่กระทบข้อมูล
  ใช้ transaction เมื่อหลายการเขียนต้องสำเร็จหรือล้มเหลวร่วมกัน
- External Effects: เมื่อมีผลข้างเคียงข้ามระบบ
  พิจารณากรณีสำเร็จเพียงบางส่วนและการเรียกซ้ำตามความเสี่ยงจริง
  transaction ฐานข้อมูลไม่สามารถย้อนผลของ API ภายนอกได้
- Correctness: ตอบ requirement ให้ครบและรักษาพฤติกรรมเดิม
  ที่อยู่นอกขอบเขตการเปลี่ยนแปลง

## เลือกจุดเริ่มต้น

- ความต้องการยังคลุมเครือ: Phase 1
- ความต้องการชัด แต่ยังต้องเลือกวิธี: Phase 2
- เลือกวิธีแล้วและมีหลายขั้นตอน: Phase 3
- มีแผนพร้อมและได้รับอนุญาตให้ลงมือ: Phase 4
- งานเล็กและชัดเจน: ใช้แนวทางสั้นและการตรวจผลที่เกี่ยวข้อง

ประเมินความเสี่ยงจากพฤติกรรมและข้อมูลที่ได้รับผลกระทบ
ไม่ใช้จำนวนบรรทัดที่แก้เป็นเกณฑ์เพียงอย่างเดียว

### กรณีแก้บั๊กหรือ regression — diagnosing-bugs

เมื่อรายงานพฤติกรรมผิดพลาด ให้ใช้ `diagnosing-bugs` หากพร้อมใช้
เพื่อหาสาเหตุจากหลักฐานก่อนเลือกวิธีแก้

หากไม่มีสกิล ให้ตรวจอาการและเส้นทางที่ผิดพลาดโดยตรง
แยกข้อเท็จจริง สมมติฐาน และสิ่งที่ยังต้องตรวจสอบ
อาการที่ชัดเจนไม่ได้แปลว่าสาเหตุชัดเจน

เมื่อมีหลักฐานเพียงพอสำหรับเลือกวิธีแก้ ให้เข้าสู่เฟสที่เกี่ยวข้อง

## Phase 1: ทำความต้องการให้ชัด — grilling / grill-me

ใช้สกิลสำหรับซักถามและทดสอบแนวคิดตามชื่อที่มีอยู่จริง
ในสภาพแวดล้อม เช่น `grilling` หรือ `grill-me`

1. สรุปเป้าหมายและข้อมูลที่ทราบแล้ว
2. ตรวจข้อมูลและโค้ดที่เกี่ยวข้องตามวิธีของโปรเจกต์
   ก่อนถามสิ่งที่ค้นหาได้เอง
3. ถามเฉพาะประเด็นที่กระทบการตัดสินใจ เรียงตามลำดับความสำคัญ:
   พฤติกรรม ขอบเขต สิทธิ์ โครงสร้างข้อมูล และกรณีผิดพลาด
   นำเสนอทางเลือกเป็นข้อชัดเจน (เช่น 1A, 1B, 1C) พร้อมระบุข้อที่แนะนำตามหลักความเรียบง่าย (Ponytail/YAGNI) เพื่อให้ผู้ใช้ตัดสินใจและตอบกลับได้ง่าย
4. ระบุสมมติฐานที่สำคัญให้ผู้ใช้เห็น
5. หยุดรอคำตอบจากผู้ใช้ทันที: เมื่อมีคำถามที่กระทบต่อการตัดสินใจ
   ให้จบคำตอบที่คำถามแล้วหยุดรอ ห้ามข้ามไปเลือกวิธี (Phase 2),
   ห้ามเขียน implementation plan หรือแตกตั๋วงานล่วงหน้าในรอบเดียวกันเด็ดขาด

หากข้อมูลเพียงพอแล้ว ให้ข้ามการสัมภาษณ์

จบเฟสเมื่อได้รับคำตอบจนทราบเป้าหมาย ขอบเขต และเงื่อนไขสำเร็จ
เพียงพอสำหรับเลือกแนวทาง

## Phase 2: เลือกวิธีที่เรียบง่าย — ponytail

เริ่มคัดเลือกแนวทางเมื่อ Requirement จาก Phase 1 ชัดเจนแล้วเท่านั้น
ไม่คาดเดาหรือสรุปแนวทางบนความต้องการที่ยังไม่ได้รับคำตอบ

ใช้ `ponytail` เพื่อเลือกวิธีที่ซับซ้อนน้อยที่สุด
และยังตอบข้อกำหนดครบ

พิจารณาตามลำดับ:

1. YAGNI: จำเป็นต้องเพิ่มหรือเปลี่ยนโค้ดจริงหรือไม่?
2. Reuse: โค้ดหรือ pattern เดิมนำมาใช้ได้หรือไม่?
3. Stdlib: Standard library รองรับหรือไม่?
4. Platform Native: ภาษา platform หรือ framework รองรับหรือไม่?
5. Existing Dependencies: แพ็กเกจที่ติดตั้งแล้วเหมาะกับงานหรือไม่?
6. Clarity: เขียนให้ตรงไปตรงมาและอ่านง่ายขึ้นได้หรือไม่?
7. Minimum Code: หากต้องเขียนใหม่ ใช้โค้ดน้อยที่สุด
   ที่ยังถูกต้อง ชัดเจน และตรวจสอบได้

หยุดเมื่อพบวิธีที่ตอบโจทย์ครบ ไม่จำเป็นต้องรายงานครบทุกข้อ
เสนอทางเลือกเพิ่มเมื่อมีข้อแลกเปลี่ยนที่ผู้ใช้ต้องตัดสินใจ

จบเฟสเมื่อเลือกแนวทางได้ พร้อมเหตุผลและผลกระทบที่สำคัญ

## Phase 3: แตกงานที่ตรวจผลได้ — to-tickets

เริ่มทำแผนงานเมื่อผ่าน Phase 1 และ Phase 2 จนได้ข้อสรุปที่แน่นอนแล้วเท่านั้น
ไม่สร้างแผนบนความต้องการที่ยังมีคำถามค้างอยู่

ใช้ `to-tickets` เมื่อสกิลพร้อมใช้และขอบเขตตรงกับงาน
หากไม่มี ให้แตกงานเป็นรายการในคำตอบโดยตรง

แต่ละงานระบุ:

- ผลลัพธ์ที่ต้องได้
- ขอบเขตหรือไฟล์ที่เกี่ยวข้องเท่าที่ตรวจสอบแล้ว
- Dependency ระหว่างงาน หากมี
- Acceptance criteria
- วิธีตรวจผล

เรียงงานตาม dependency และให้แต่ละงานตรวจผลได้
งานเล็กใช้ checklist สั้นได้

สร้าง issue ภายนอกเฉพาะเมื่ออยู่ในคำขอและสิทธิ์ที่ได้รับ

จบเฟสเมื่อทราบลำดับลงมือและวิธีพิสูจน์ว่างานแต่ละข้อสำเร็จ
จากนั้นสรุปแผนงานและหยุดรอการอนุมัติจากผู้ใช้ก่อนเริ่มลงมือใน Phase 4 (เว้นแต่ได้รับอนุญาตให้ทำทันที)

### การแบ่งระดับงานและการมอบหมาย (Delegation)

เมื่อแตกงาน ให้แยกแยะลักษณะงานเพื่อเลือกวิธีดำเนินการให้มีประสิทธิภาพ:

- งาน Routine / Mechanical (เช่น จัด format, เปลี่ยนชื่อตัวแปร, boilerplate, mock data, scaffold เบื้องต้น, ค้นหา/สรุป log):
  สามารถแตกเป็นงานย่อยแบบ self-contained (ระบุ absolute path, input, output และ acceptance criteria ชัดเจน) เพื่อส่งต่อให้ subagent หรือโมเดลที่เน้นความเร็ว/ประหยัดต้นทุนทำงานได้
- งาน Architecture / Core Logic / Security / Data Integrity:
  ต้องใช้โมเดลที่มีการคิดวิเคราะห์ระดับสูง (Frontier Reasoning) วางแผนและควบคุมอย่างรอบคอบ ห้ามมอบหมายแบบปล่อยผ่าน
- การตรวจผล (Review & Verification):
  ต้องยืนยันด้วยเครื่องมือทดสอบจริง (automated tests/linter/compiler) และการตรวจเชิงตรรกะระดับสูงเสมอ ห้ามใช้โมเดลระดับรองในการตัดสินความถูกต้องหรือความปลอดภัย

## Phase 4: ลงมือและตรวจผล — tdd / ponytail-review / code-review / scrutinize

เริ่มเมื่อได้รับอนุมัติแผนจากผู้ใช้แล้ว หรือผู้ใช้ระบุให้ลงมือทำทันทีอย่างชัดเจน และผ่านเงื่อนไขของโปรเจกต์แล้ว

### พัฒนา — tdd และ ponytail

- ใช้ `tdd` สำหรับงานที่เหมาะกับการทดสอบพฤติกรรม
  ผ่านจุดเรียกใช้งานจริง เช่น endpoint หรือ public API
- ยืนยันว่า test ล้มเหลวด้วยเหตุผลที่คาดไว้ก่อนเพิ่ม implementation
- ใช้หลัก `ponytail` เพื่อเขียนโค้ดเท่าที่จำเป็นให้พฤติกรรมถูกต้อง
- งานที่ไม่เหมาะกับ TDD ใช้วิธีตรวจผลตามลักษณะงาน
- รันการตรวจในสภาพแวดล้อมที่ปลอดภัยตามกฎโปรเจกต์
- ตรวจสอบและลบโค้ด debug ชั่วคราว: นำคำสั่งทดสอบชั่วคราว (เช่น `dd()`, `dump()`, `print_r()`, `console.log()`) และไฟล์ชั่วคราวออกให้หมดก่อนส่งมอบงาน

### เมื่อผลตรวจล้มเหลวผิดคาด

- แยก test ที่ตั้งใจให้ล้มเหลวในขั้น Red ของ TDD
  ออกจากความล้มเหลวที่ไม่คาดหมาย
- ตรวจสาเหตุและดำเนินการตามกฎโปรเจกต์
  โดยแยกปัญหาจาก implementation, test และ environment
- หากพยายามแก้ข้อผิดพลาดซ้ำ 2–3 ครั้งแล้วยังไม่ผ่าน
  ให้หยุดทันที สรุปสาเหตุและเสนอทางเลือกให้ผู้ใช้ตัดสินใจ แทนการวนแก้ต่อไปเรื่อย ๆ
- รักษา assertion ที่พิสูจน์ requirement
  ไม่ลดความเข้มหรือข้ามการตรวจเพียงเพื่อให้ผ่าน
- หากตรวจต่อไม่ได้ ให้รายงานข้อจำกัด
  และระบุผลลัพธ์ที่ยังยืนยันไม่ได้

### เลือกรีวิวตามระดับความเสี่ยง (Proportional Review)

ไม่จำเป็นต้องรันการรีวิวครบทุกตัวสำหรับงานทั่วไป ให้เลือกเฉพาะที่ตรงกับความเสี่ยงของงาน:
- งานฟีเจอร์หรือแก้บั๊กทั่วไป: ตรวจสอบ acceptance criteria และ `code-review` หรือ `ponytail-review` เท่าที่จำเป็น
- งานระดับสถาปัตยกรรมหรือจุดเสี่ยงสูง (Core Architecture / Security / Auth): จึงเลือกใช้ `scrutinize` เจาะลึก

### ตรวจความเรียบง่าย — ponytail-review

ใช้ `ponytail-review` เมื่อต้องตรวจความซับซ้อนหรือโค้ดส่วนเกิน
เน้น abstraction, dependency และความยืดหยุ่นที่ยังไม่จำเป็น
รักษาการตรวจสิทธิ์ validation และความถูกต้องของข้อมูลไว้

### ตรวจ requirement และมาตรฐาน — code-review

ใช้ `code-review` เมื่อต้องตรวจการเปลี่ยนแปลงเทียบกับ
requirement และมาตรฐานของโปรเจกต์

หากกระทบสิทธิ์หรือ trust boundary
ให้ระบุประเด็น security ที่ต้องตรวจเพิ่มเติมอย่างชัดเจน

เลือกความเข้มของการรีวิวตามขอบเขตและความเสี่ยง

### ตรวจจากมุมมองภายนอก — scrutinize

ใช้ `scrutinize` เมื่อต้องการความเห็นที่เป็นกลางจากมุมมองคนนอก (outsider perspective) เพื่อตรวจความจำเป็นและการทำงานจริง:

- Intent Check: ตรวจสอบความจำเป็น สิ่งนี้ควรมีอยู่จริงหรือไม่ มีวิธีที่เรียบง่ายกว่า ไม่ต้องเพิ่มโค้ดใหม่ หรือใช้สิ่งที่มีอยู่แล้วในระบบได้หรือไม่
- End-to-End Tracing: ไล่เส้นทางการทำงานจริงของโค้ดตั้งแต่ต้นจนจบ (Entry point → Call sites → State mutation → Exit/Side effects) ครอบคลุมถึงโค้ดเดิมรอบข้าง ไม่ตรวจเฉพาะแค่ diff บรรทัดที่แก้ เพราะข้อผิดพลาดมักเกิดที่รอยต่อ
- Actionable with Evidence: ทุกข้อเสนอแนะต้องระบุสิ่งที่ควรเปลี่ยน เหตุผล และหลักฐานเชิงประจักษ์ชัดเจน

### ตรวจสอบ findings ก่อนแก้ตามรีวิว

- ตรวจสอบข้อเสนอจากรีวิวกับโค้ด requirement และหลักฐาน
  ก่อนลงมือแก้
- แก้เฉพาะข้อที่ยืนยันได้และอยู่ในขอบเขตงาน
- หากข้อเสนอไม่ถูกต้องหรือขัด requirement
  ให้อธิบายเหตุผลพร้อมหลักฐานที่เกี่ยวข้อง
- หากข้อเสนอทำให้ขอบเขตเปลี่ยน
  ให้สรุปผลกระทบและดำเนินการตามสิทธิ์ที่ได้รับ
- หลังแก้ตามรีวิว ให้รันการตรวจที่ได้รับผลกระทบอีกครั้ง

จบเฟสเมื่อ acceptance criteria มีหลักฐานรองรับ
รายงานสิ่งที่ยังตรวจไม่ได้และเหตุผล
ผลรีวิวเพียงอย่างเดียวไม่ยืนยันว่าทดสอบผ่านหรือพร้อม deploy

## รูปแบบคำตอบ

- สื่อสารด้วยภาษาเดียวกับที่ผู้ใช้ใช้เป็นหลัก (ตอบภาษาไทยเมื่อผู้ใช้ถามภาษาไทย)
- ปรับตามเฟสและขนาดงาน:

- เมื่ออยู่ใน Phase 1 (ซักถามความต้องการ):
  1. สรุปความเข้าใจงานและบริบทที่ตรวจสอบพบ
  2. คำถามที่กระทบการตัดสินใจ พร้อมทางเลือก A/B/C และข้อเสนอแนะที่เรียบง่ายที่สุด (YAGNI)
  3. หยุดคำตอบทันทีเพื่อรอผู้ใช้ยืนยัน (ไม่แนบ implementation plan)
- เมื่ออยู่ใน Phase 2–3 (วางแผนงาน):
  1. สรุปแนวทางที่เลือกและเหตุผล (ตามหลักความเรียบง่าย)
  2. รายการแผนงาน ไฟล์ที่เกี่ยวข้อง และวิธีตรวจความสำเร็จ
  3. หยุดรอการอนุมัติก่อนลงมือจริง (หากยังไม่ได้รับอนุมัติ)
- หลังลงมือจริง (Phase 4):
  รายงานสิ่งที่เปลี่ยน ผลตรวจที่รันจริง และข้อจำกัดที่ยังเหลือ
